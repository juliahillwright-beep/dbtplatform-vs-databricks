dbt platform with Databricks

Databricks runs your data. dbt platform governs how it becomes trusted.

dbt platform is not an alternative to Databricks. It is the transformation and developer layer that runs on top of it — modular SQL, tests that run before production, model-aware CI/CD, and a governed semantic layer that reaches past Databricks-native tools.

Division of labor

The question is not dbt or Databricks

Most teams evaluating this are really answering two separate questions that got bundled into one. Choosing Databricks for compute, storage, and governance is an infrastructure decision. Choosing Databricks to own your transformation logic is a strategic one. Most organizations sign off on the first without realizing they also made the second.

Here is how the layers actually divide.

Layer Databricks (native) dbt platform
Ingestion and streaming DatabricksLakeflow Declarative Pipelines for bronze and continuous real-time ingestion Not the primary use case. dbt is not designed for streaming ingestion
Transformation, silver → gold SQL in notebooks or Lakeflow pipelines. Logic often spread across notebooks and jobs dbtModular, version-controlled SQL models. The standard layer for reusable, testable business logic
Orchestration DatabricksLakeflow Jobs and Declarative Automation Bundles for orchestrating the broad estate Model-level orchestration that gates on data tests, not just job success. dbt State compares code and data freshness and reuses or clones unchanged models
Governance DatabricksUnity Catalog for access control, row and column security, audit, and discovery Project-level governance: tests, documentation, macro and UDF context, lineage of transformation logic — with metadata pushed back into Unity Catalog
Semantics and metrics Unity Catalog metric views: governed, materialized, strong for Databricks-native consumers Governed semantic layer with first-party integrations across BI, spreadsheet, notebook, and AI tools, plus JDBC, GraphQL, and Python APIs

Databricks is the right place to run the platform. The real question is whether you want Databricks alone, or Databricks with a faster, less expensive, and more reliable transformation workflow running on top of it.

The inflection point

Databricks works. Then the analysts arrive.

Most Databricks estates start with a data engineering team of roughly ten people who are fluent in Python, Spark, notebooks, and infrastructure. That team can build almost anything, and for the first year or two it does.

Then the analytics and business teams show up — fifty, two hundred, five hundred people who are SQL-first and who need governance, tests, and lineage at a scale that tribal knowledge cannot cover. The bottleneck is no longer capability. It is the width of the front door.

Notebooks stop scaling here. Not because Databricks is the problem, but because notebooks were built for exploration, not for the production analytics surface the business now depends on. Three things go wrong at the same time.

01

The contributor pool stays narrow

A SQL-fluent analyst cannot realistically contribute to a PySpark notebook framework. Every model request routes back through the engineering team, and the engineering team becomes the queue.

02

Every shop builds its own framework

The macro library, the test helpers, the deployment wrapper — all invented locally, all living in the heads of two or three senior engineers. Versions drift through Git installs pinned to a branch rather than a release, so one merge can silently break forty notebooks. Impact analysis becomes a text search.

03

Contracts break at runtime, not compile time

A notebook is procedural. It runs, and then you find out. The dependency graph exists in practice but not in a form anything can inspect before execution.

What dbt platform adds

Seven things the native stack does not give you

01

Tests run before the data moves

Native

Expectations validate data at runtime, after it has already moved — not in code review.

dbt platform

Tests run in the pull request. The bad join never merges.

  • Generic, custom, singular, and unit tests, plus contracts and source freshness
  • Packages like dbt_utils, dbt_expectations, and audit_helper ship maintained tests. Native quality checks are typically built by hand
  • A metric on an untested table returns a confidently wrong answer. An agent amplifies it rather than catching it
02

Analysts can contribute

Native

Pipeline authoring is engineering-led. Every model request queues behind ~10 engineers.

dbt platform

SQL-fluent analysts ship models inside guardrails set once. The pool becomes 50–500.

  • No Spark or notebook expertise required to write, test, and review a model
  • Lakeflow Pipelines Editor and Genie Code lower the pipeline-author floor — but that is not the modeling layer
  • It changes who sits closest to the business logic — where most quality problems start
03

The dependency graph builds itself

Native

Dependencies are inferred inside a pipeline you defined. Across pipelines and jobs, you wire them by hand.

dbt platform

Write ref() and the graph for the whole project falls out of the code. There is no framework to adopt first.

  • One project-wide DAG, resolved at parse time and inspectable before anything runs
  • Impact analysis is a query against the graph, not a text search across notebooks
  • The graph cannot drift from the code, because it is derived from it
04

CI/CD in the platform, not assembled by hand

Native

The unit of work is the pipeline. Refresh the whole thing, and CI cost scales with pipeline size.

dbt platform

The unit of work is the model. state:modified+ builds only the changed subgraph, in an isolated PR schema.

  • CI/CD ships with the platform. The native path is do-it-yourself — Declarative Automation Bundles plus GitHub Actions you build, own, and maintain
  • dbt State compares code and data freshness in production, skipping or cloning what did not move
  • Cost Insights attributes spend per model, so compute savings are measurable rather than asserted. dbt State is in preview

Nothing is duplicated. Lakeflow Jobs stays the top-level orchestrator. dbt runs inside it as a task type.

05

The context Unity Catalog does not capture

Native

Table and column lineage, scoped to Databricks.

dbt platform

Why a model exists, what it is tested against, who owns it, how logic flows through macros — pushed back into Unity Catalog.

  • Generated by doing the work, not maintained separately
  • Lineage spans projects via dbt Mesh, with public model boundaries and versioned contracts
06

Governed metrics with broader reach

Unity Catalog metric views went GA in April 2026. The gap is not existence — it is reach and testability.

Native

Governed in Unity Catalog. Strong for Databricks-native consumers.

dbt platform

Live today in Tableau, Power BI, Sigma, Mode, Omni, Lightdash, Hex, Excel, and Sheets, plus JDBC, ADBC, GraphQL, Python, and MCP.

  • Definitions are code, so they can be tested. Unity Catalog has no first-class test concept for metric definitions
  • Simple, ratio, cumulative, derived, and conversion metrics, including definitions that span sources
  • Genie Code can consume the dbt MCP server through a Unity Catalog connection — dbt feeds Genie rather than competing with it. Today that runs in Genie Code Agent mode, in Model Serving regions, capped at 20 tools
07

Logic that is not welded to one engine

Native

Spark-authored transformation logic runs on Databricks. Federation and Iceberg move the data, not the logic.

dbt platform

The same project runs on Databricks, Snowflake, BigQuery, Redshift, and Fabric.

  • Relevant today if you already run Databricks alongside another warehouse — roughly half of enterprises using dbt work across more than one platform
  • Relevant later as insurance: a platform decision three years out does not become a rewrite of every model

Deliberately last. Portability is not the reason to adopt dbt — it is what makes the decision cheap to revisit. If Databricks is the only engine you will ever run, skip this one.

Honest limits

Where the native stack wins

Four cases where we would not put dbt in the path.

Streaming and sub-minute latency

Lakeflow Declarative Pipelines, not dbt. Bronze belongs there. Worth checking the real requirement though — hourly or better sits well inside dbt's range.

CDC and SCDs at the ingestion boundary

AUTO CDC and native SCD Type 1 and 2 are mature and well-integrated. Use them.

Genuinely Databricks-only teams

With no multi-platform ambition, Unity Catalog metric views plus Genie is a valid native path for semantics. The testing argument still stands. The portability one does not.

Broad estate orchestration

Lakeflow Jobs stays on top. dbt runs inside it as a task type.

Federation and Iceberg expose output data to other engines. They do not make the logic portable. Portable data is not portable logic.
